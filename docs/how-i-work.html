Approach

How I work with AI

At work I designed and built an agentic delivery system for a BI team. This page describes the method, not the work it was used on: how AI agents are given jobs, checked and stopped, so that one team can run many projects with a human still in charge.

Two terms you will see: overseer (a lead agent that runs the project) and parity check (the numbers before and after a change must match).

Four principles

Short on purpose.

  1. Code first, AI at judgement points

    Plain code for anything deterministic. AI only where a judgement is needed, with its output validated.

  2. Review before production

    Independent review, tests and a human sign-off before anything reaches production.

  3. Small and boring wins

    Small, boring systems beat clever ones. The story further down is how I learned it.

  4. Log what the AI decided

    Measure and log what the AI decided so a person can check it.

A change starts with me and the overseer (a lead agent that runs the project), which plans the work and passes scoped slices to specialists. The analyst profiles the data. A proposal with backup and rollback is the first gate. The builder makes the change, an independent reviewer checks it and the tester uses it as a user would. A parity check (the numbers before and after must match) compares key figures against the baseline, and if one moves that should not, the change goes back to the builder. Then I give a human sign-off for that specific change, and the release manager does a dry run, releases and verifies. The control room watches every overseer throughout.     The method in full

    Eight parts, one idea

    The map above, in words.

    Overseer and specialists

    Each project gets one lead agent, the overseer, which runs the project. It holds the plan, talks to me, and hands scoped slices to specialist agents: an analyst (requirements and data profiling), a builder, an independent reviewer, a tester and a release manager. Only one agent writes a given file at a time. The overseer checks what comes back before anything reaches me, and specialists never approve their own work.

    A living state document

    Every project keeps one document: workstreams, decisions with dates, what is waiting on whom, key IDs. Agents read it first after a break, so work survives a restart and every decision has a paper trail.

    Gates, not trust

    Read-only by default. Changes are proposed with what, why, impact, backup and rollback before they are applied. Nothing reaches production without my explicit go for that specific change. Releases are dry-run first.

    Parity checks

    The numbers before and after must match. Before and after every change to a report or model, the key figures are compared value by value against a baseline. If a number moves that should not, the change does not ship. That is what makes a redesign safe to hand to leadership.

    Independent verification

    Answers to data questions are rechecked by a separate agent that did not produce them.

    Toolkits per platform

    Packaged, reusable toolkits for Power BI reports, Fabric apps and Power Platform, so every job starts from the same rules, roles and templates rather than from scratch.

    A control room

    A small local dashboard to watch all the overseers and their agents at once, see what needs me, and message them, with a policy on which agents may talk to which.

    The right model for the job

    The cheapest model that does the task well; the most capable one only where judgement or design quality matters.

    A lesson learned

    The toolkit that became the project

    My first personal version of this system grew into its own project. I spent two days building the system itself, and almost none of it served the goal. An independent audit called it over-engineered. It was right, so I wrote up why and rebuilt it small: a Claude Code plugin with researcher, analyst, designer, builder, tester and reviewer roles, and build and maintain skills.

    The system must not become the project. Small and boring beats clever.

    The lesson I carry into work: the system exists to ship things. Keep it small, keep the human out of the message-bus role, and have the assistant push back instead of agreeing.

    The rules that came out of it

    1. The system must not become the project.
    2. Don’t make yourself the message bus.
    3. Short chats over long-lived ones.
    4. The assistant should push back.

    The gain

    One team can run many projects in parallel, each supervised and each with an audit trail.
